## 2. Agent roster

| Agent | Runtime | Role | Model (fallback) | Tools and permissions |
|---|---|---|---|---|
| architect | Hermes Agent | Architecture note, tickets with acceptance criteria, re-plans on escalation | _TBD (strongest)_ | `gh` issues/labels; may only write `docs/ARCHITECTURE.md` |
| lead | Hermes Agent | Dispatch: assigns, re-queues, catches stuck or repeatedly failing work, Run log | _TBD (cheap)_ | `gh` issues/labels/comments; no code |
| builder-core | OpenClaw | Builds `area:core` tickets: validator, generator, retry, database, limits | _TBD_ | branches, PRs; no merge; cannot touch `infra/`, `agents/`, `.github/` |
| builder-web | OpenClaw | Builds `area:web` tickets: pages, gallery, safe display, Caddy, deploy | _TBD_ | same as builder-core |
| reviewer | Hermes Agent | Approves or rejects each PR against its ticket | _TBD (strong, different family from builders)_ | comments, labels; no code |
| tester | OpenClaw | Tests approved PRs, bad specs, post-deploy check | _TBD (small)_ | run commands, file bugs, labels; no product code |
| human (Vyom) | n/a | Approves and merges; decides escalations | n/a | full |

Why six and not more: the free model tiers allow roughly one request at a time per provider, the VM is small,
and every agent must have real work to show. A red-team agent and a docs agent are planned additions once the
core is merged. Why the reviewer is not the lead: the lead decides when work goes back, so it should not also
judge the work; review also needs a stronger model than dispatching does.

Role prompts: `agents/<name>/ROLE.md`. Shared rules: `agents/PROTOCOL.md`. Product requirements: `PLAN.md`.

## 3. How a ticket moves from idea to merged code

```
PLAN.md -> architect: docs/ARCHITECTURE.md + tickets (area:core | area:web) -> lead
  lead assigns -> status:ready + agent:builder-core | agent:builder-web
    builder claims -> status:in-progress -> PR opened -> status:needs-review -> reviewer
      reviewer -+- reject  -> review:changes-requested -> lead: back to builder (attempt 2)
                |                                         or, after 2 failures, escalate to architect -> human
                +- approve -> review:approved -> status:needs-test -> tester
          tester -+- fail -> test:failed + [BUG] issue -> lead triages (architect if it needs design)
                  +- pass -> test:passed -> lead: status:ready-to-merge -> human approves and merges
                                -> auto-deploy -> tester post-deploy check
```

Gates that actually block: `.github/workflows/merge-gate.yml` fails unless `review:approved` and `test:passed`
are present and no rejection label is; new commits remove both labels; agents' token lacks `workflow` scope,
so they cannot edit the gate; branch ruleset requires the check and a human approval.

Cost control: a small wake-up script (plain code, not a model) checks GitHub before starting an agent, so an
agent with nothing to do costs no tokens.

## 8. Reproduce

```bash
# 1. One VM (pick the provider folder you can use)
cd infra/<oracle|aws> && terraform init && terraform apply
ssh ubuntu@$(terraform output -raw public_ip)

# 2. On the VM: everything else
git clone https://github.com/vyomya/agent-studio && cd agent-studio
sudo ./scripts/install.sh            # first run writes /srv/agent-studio/.env from agents/env.example; fill it in
sudo ./scripts/install.sh --start    # runtimes, 6 agents, workspaces, test DB, wake-up timers, product deploy
```

`install.sh` is safe to run again; `--update-agents` refreshes only the agents' rules and config.
